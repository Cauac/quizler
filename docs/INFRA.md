# Infrastructure and delivery

Decided stack is in [TECH_CONSTRAINTS.md](TECH_CONSTRAINTS.md). This document describes how it is built and shipped.

## Decisions
* One environment: `production`. No staging.
* Terraform lives in `infra/`. It is planned and applied from the owner's machine.
* Terraform state is in the S3 bucket `quizler-terraform` (eu-north-1) with native locking (`use_lockfile`). The bucket was created by hand, is not managed by Terraform, and has versioning, encryption and a public access block enabled.
* Domain: `quizler.app`, registered at Namecheap and attached: its nameservers point to a Route 53 hosted zone managed by Terraform (`infra/dns.tf`). Captains reach the app through a QR code on the big screen, so the name only needs to be short and easy to read aloud; SEO is not a concern. The `.app` TLD is HSTS-preloaded, so it is HTTPS-only. The domain is easy to replace if needed.
* No load balancer. Traffic path: browser → CloudFront (`quizler.app`, `www.quizler.app`, ACM certificate in `us-east-1`) → the public IP of the Fargate task, plain HTTP on port 8080.
  * The network is a dedicated VPC with two public subnets, an internet gateway, no NAT and no private subnets (`infra/network.tf`).
  * The task's security group admits TCP 8080 only from the AWS-managed prefix list `com.amazonaws.global.cloudfront.origin-facing`. That list uses about 55 of the 60 default rules per security group, so the group holds nothing else.
  * There is no secret origin header, so someone with their own CloudFront distribution could reach the origin. This is accepted for now. Adding an ALB later only changes the origin and the security group.
  * CloudFront has the origin read and keep-alive timeouts at 60 s, so SSE needs a heartbeat more often than every 60 s. Caching is off and all viewer headers except `Host` are forwarded (managed policies).
* The server runs as one ECS Fargate task (ARM64, 0.5 vCPU / 1 GB) of the service `quizler-server` in the cluster `quizler`. The deployment config is minimum healthy 0% and maximum 100%: the old task stops before the new one starts, so there are never two servers. A deploy therefore causes a short outage, and **nothing is pushed to `main` during a game**.
* The server is stopped except during games (idle cost is about $1/month: the Route 53 hosted zone). The owner starts and stops it by hand; the service's desired count is 0 otherwise.
  * `infra/scripts/start.sh` sets the desired count to 1, waits for the service to be stable, runs `sync-origin-dns.sh`, then polls `https://quizler.app/health` and reports the cold-start time. It is safe to re-run while the service is up.
  * `infra/scripts/stop.sh` sets the desired count to 0, resets the origin DNS record (see below) and waits until no tasks are running.
  * `.github/workflows/stop.yml` is a safety net: it sets the desired count to 0 and resets the origin DNS record at midnight UTC (`cron: "0 0 * * *"`) in case `stop.sh` was forgotten, and can be run by hand (`workflow_dispatch`). GitHub may delay scheduled runs by tens of minutes, and **disables scheduled workflows in a public repository after 60 days without repository activity**; if that happens, re-enable the workflow in the Actions tab.
  * Terraform ignores `desired_count` and `task_definition` of the service, so a local apply neither stops a running game nor rolls back a release.
* DNS: `quizler.app` and `www.quizler.app` are alias records to CloudFront. `origin.quizler.app` is an A record (TTL 60) with the current task's public IP and is CloudFront's origin. Terraform creates it with the placeholder `192.0.2.1` (RFC 5737) and ignores its value.
  * A stopped service must not leave its IP in DNS: the address returns to the AWS pool and could be given to someone else, who would receive CloudFront's requests (cookies, `Authorization` headers) and answer under our certificate. So `stop.sh` and `stop.yml` run `infra/scripts/reset-origin-dns.sh`, which sets the record back to the placeholder right after scaling to 0 (and also when the service is already stopped). The deploy role may change this record (and only this one, see below).
  * `infra/scripts/sync-origin-dns.sh` finds the single running task, reads its public IP and UPSERTs the record, then waits for the change to be `INSYNC`. It fails unless exactly one task is running. It uses whatever AWS credentials are set and finds the hosted zone by the domain name (`route53:ListHostedZonesByName`; `HOSTED_ZONE_ID` overrides the lookup). `reset-origin-dns.sh` does the same. `start.sh` and the deploy workflow run it after the service is stable. There is no Lambda or EventBridge.
  * If ECS replaces a crashed task, the new task has a new IP and the site stays down, and the record points at the old task's released IP until then. Recovery: run `infra/scripts/start.sh` again. If this happens in practice, add an EventBridge rule and a Lambda that update the record.
* The application is deployed by GitHub Actions (`.github/workflows/deploy.yml`) on push to `main` that touches `server/**` or the workflow file (and by hand): build the ARM64 image on a GitHub ARM runner, push it to ECR tagged with the git SHA (tags are immutable, so if that tag already exists, as on a re-run for the same commit, the build and push are skipped), register a new ECS task definition revision with that image and the `GIT_SHA` environment variable, and update the service. If the service is running (desired count 1) the workflow then waits for it to be stable and runs `sync-origin-dns.sh`; if it is stopped, the new revision applies at the next start.
  * GitHub authenticates to AWS with OIDC. No AWS keys are stored in GitHub.
  * The deploy role `quizler-deploy` (`infra/github.tf`) is trusted only for the `main` branch of this repository (scheduled workflows run on `main` too). The repository issues GitHub's immutable OIDC subject claims, so the trust condition is `repo:Cauac@<owner id>/quizler@<repo id>:ref:refs/heads/main` with the numeric IDs (see `infra/github.tf`); the classic `repo:Cauac/quizler:...` form would not match. If the repository is renamed, transferred or recreated, update the IDs. It can push to and describe images in the ECR repository, register task definitions, update this ECS service, pass the task roles, and what the DNS scripts need (list and describe tasks, describe network interfaces, find the hosted zone, change records in it). `route53:ListHostedZonesByName` is read-only and cannot be limited to one zone. Changing records is restricted by IAM conditions to `UPSERT` of `A` records named `origin.quizler.app`, so a compromised workflow on `main` cannot touch the apex, `www` or the ACM validation records.
  * One GitHub Actions repository **variable** (not a secret) is set by hand from a Terraform output: `AWS_DEPLOY_ROLE_ARN` (`deploy_role_arn`).
  * The image build uses `docker/build-push-action` with the GitHub Actions cache, so unchanged Maven dependencies are not downloaded again.
  * **How task definition changes ship.** CI registers each new revision by copying the latest revision and replacing the image and `GIT_SHA`. So a change to the task definition in Terraform (CPU, memory, env, logging) takes effect at the next deploy, not at `apply`; the service ignores Terraform's own revision. The copy keeps only the fields listed in the `jq` filter in `deploy.yml`; any other field (for example `ephemeralStorage` or `pidMode`) is dropped silently, so add it to the filter when you start using it. Revisions registered by CI do not get the `Project` and `ManagedBy` tags that Terraform's default tags put on its own revision.
  * The ECR repository `quizler-server` has immutable tags, scan on push, and keeps the last 10 images. The task definition created by Terraform references `quizler-server:bootstrap`, which does not exist; CI replaces it with the first real image before the service is ever started.
* The database is an Aurora DSQL cluster, managed by Terraform in `infra/`. It uses IAM authentication only; the ECS task role gets `dsql:DbConnect` on the cluster. The database role and its `AWS IAM GRANT` are created once by hand with an `admin` token (see [TECH_CONSTRAINTS.md](TECH_CONSTRAINTS.md)). It is reached over its public endpoint, so no VPC endpoint is created.
* The DSQL cluster is defined in `infra/dsql.tf` with deletion protection on. The `quizler-terraform` user gets `dsql:DbConnectAdmin` on it for the one-time role setup. The endpoint is the `dsql_endpoint` Terraform output.
* Media files are in the S3 bucket `quizler-media`, managed by Terraform (`infra/media.tf`). It is private (public access block, bucket-owner-enforced ownership, SSE-S3 encryption); clients read through presigned URLs only. IAM access for the ECS task role is added together with the server code that uses it.
* The repository is public, so workflow logs are public. Secret values are never managed by Terraform; it creates the secret containers only.

## Running Terraform
Scripts in `infra/scripts/` (they refuse to run as any identity other than the Quizler IAM user):
* `get-credentials.sh` signs in to the private AWS account.
* `plan.sh` shows the changes.
* `apply.sh` applies them after confirmation.
* `start.sh` and `stop.sh` start and stop the server (see above).

## First-time setup
1. `apply.sh -target=aws_route53_zone.main` creates only the hosted zone. Its nameservers are the `name_servers` output.
2. At Namecheap, set the domain's nameservers to those four. Wait for propagation (`dig NS quizler.app`).
3. `apply.sh` creates the rest. ACM validation completes once DNS is delegated. The service exists with 0 tasks.
4. Set the repository variable `AWS_DEPLOY_ROLE_ARN` from the Terraform output, then push to `main` or run the Deploy workflow to build and deploy the first image.
5. Run `start.sh` and open `https://quizler.app`.
